# Correctness, performance and memory audit

Reviewed the Python calculation, parsing, persistence, workflow, provider and API modules; browser request/state handling, rendering and WebGL ownership; deployment/startup configuration; and existing regression coverage. Changes were made in place. This workspace has no Git repository, so no baseline commit or Git diff was available.

## Fixed

| Area | Finding and change |
| --- | --- |
| Text editor | In-flight analysis could render after subsequent edits, and saving could associate an earlier document with later text. Edits now invalidate results immediately, abort superseded analysis requests, and disable stale saves. Saves capture the actual submitted text and are serialized. |
| Dashboard | Results from a replaced document could overwrite current statistics. Results and errors are now applied only to the originating document. |
| Quick editing | The grid rewrites costs as zero and weights as one. Documents with nonzero costs or custom weights now open in the full form, preserving those inputs. |
| WebGL | Shader/program setup failures bypassed cleanup. Buffers and shaders were not explicitly released, and animation closures retained the CPU upload buffer. Cleanup now owns partial allocations, explicitly deletes GPU objects, disconnects observers and cancels frames. CPU data is allocated directly into one typed array and released after upload. |
| Provider response | Clarification responses were buffered without a size limit. They now stream with a 300,000-byte limit and close on success, rejection or failure. |
| Game parser | Sparse input could expand into a large Cartesian payoff table and missing-cell list. Parsing now rejects more than 30 choices per player before table construction. |
| Backup scheduling | Daily-backup check and date update were outside the shared lock. Scheduler/request races could create duplicate backups. The whole operation is now serialized. |
| App lifecycle | Background backup cancellation now runs in a finally block, including exceptional shutdown. |
| Profile versions | Duplicate-version checking and insertion could race. Both now use the Store lock. |
| Validation | One-sided probability bounds are checked against point probabilities. Malformed retrieval pins and queries return validation errors instead of crashes or coercion. |
| Statistics | Each distribution is sorted once instead of repeatedly for each quantile and tail. Simulation quantiles sort distinct values and use cumulative counts instead of sorting all samples. |
| Browser allocations | Number formatters are reused, and the decision tree builds a parent-to-children map instead of scanning all nodes for each node. |

## Verification

- Python suite after the follow-up pass: **236 passed**, one existing Starlette/httpx test-client deprecation warning.
- Browser/DOM/API integration suite: **28 passed**.
- Instrumented WebGL tests: 100 redraws retain exactly one active program, buffer, observer and animation frame. Final cleanup leaves zero tracked resources. Compilation, linking and upload failure paths also leave zero. The tests deliberately omit the optional context-loss extension.
- Provider regression verifies that an oversized streamed response stops consumption and closes its stream.
- Added regressions for asynchronous saves/results, quick-editor compatibility, bounds, retrieval validation, concurrent daily backups and sparse-game expansion.

Run `npm test`, `.venv/Scripts/python.exe -m pytest -q`, and `.venv/Scripts/python.exe scripts/audit_memory.py` to reproduce checks.

## Measurements and limits

A local synthetic benchmark of 100,000 samples over 100 distinct values compared the previous and current summary routines, with identical returned results:

| Measurement | Before | After |
| --- | ---: | ---: |
| Median seconds per summary | 0.02173 | 0.01441 |
| Peak temporary Python allocation | 1,195,320 bytes | 39,600 bytes |

This is approximately 34% less runtime and 97% less peak allocation for that routine and input, not an application-wide speed claim. Input allocation is excluded; timing is measured separately from tracing.

Repeated synthetic quick-analysis/cache/retrieval batches kept the configured cache at eight entries and the repeatedly updated retrieval index at one record. Traced retained bytes across four batches were 24,608, 33,944, 37,618 and 40,361. This small growth does **not** establish a steady-state plateau or prove the absence of every leak.

The analysis cache already has entry and byte limits. Retrieval intentionally retains active corpus text/vectors; memory therefore still scales with saved data. Archived/superseded retrieval entries are removed on the next synchronization, not immediately at the storage mutation. See the follow-up changes below for shared indexing and compact listings. Pagination remains a possible further improvement.

WebGL validation uses instrumented JavaScript resources, not real GPU-driver memory measurements. Python tracemalloc excludes native allocations. No long-running browser heap soak, production-load test, live model-provider call or deployment was performed. The audit fixes the demonstrated paths; it is not a guarantee that all possible errors or memory leaks have been eliminated.

## Follow-up pass

- Search and clarification sessions now share one serialized retrieval index. A cross-route regression verifies that warming search followed by session creation and another search decrypts no unchanged corpus records. Both routes now require `confirmed is True`; a contradictory legacy `status` string cannot reintroduce an unconfirmed memory.
- Memory change stamps are 32-byte SHA-256 digests rather than retained copies of entire encrypted payloads. Changes still invalidate the index, and unconfirmed records release their decoded memory copies on synchronization.
- Corpus synchronization streams SQLite rows and decodes one changed record at a time, instead of retaining a fetched list of encrypted payloads plus a list of decoded records.
- Search uses a bounded heap shortlist, retaining explicit pins and deterministic tie ordering. Nine regression combinations compare it against full sorting.
- Node and session listing endpoints accept `summary=true`. The workspace and simulation picker use these compact records. Full endpoints retain their default response shape, and opening an individual record still returns its full document and provenance. Summary projection happens while streaming decoded records, so the output list excludes snapshots, histories and frozen-parent documents.
- Simulation branch checks and maintenance candidate calculations use compact node summaries too.

The 2,000-record search benchmark retained identical results and measured **22,765 bytes** peak temporary Python allocation with the heap, versus **372,049 bytes** using full-sort selection (about **94% less**). This excludes the persistent corpus and is not a claim about total process memory. An example parent/child listing regression verifies compact JSON is less than one tenth the size of the full listing.

Final verification: **236 Python tests and 28 browser tests pass**. The integration test's initial-load assertion was updated to expect the new summary query; its real API workflow then passed.
